STATUS
Complete

OBJECTIVE
Generate correct machine code for the limited A-MIR used by the milestone (Packet WP-008).

SUMMARY
Built a small, deliberately non-general x86-64 instruction encoder (include/arco/x86_64_encoder.hpp:
an Assembler class with sub_rsp_imm8, add_rsp_imm8, mov_store_disp8, mov_load_disp8, mov_reg_reg,
mov_reg_imm64, lea_rip_relative, call_indirect_disp8, ret) implementing exactly the instruction
shapes this milestone's code needs. Before writing any C++, hand-derived the exact byte encoding
for every needed instruction and verified each one against `nasm -f bin` output (a genuinely
separate tool, not the same reasoning re-checked) -- every primitive's C++ output was then
unit-tested against those same nasm-verified byte sequences in tests/runtime_tests.cpp.

Built generate_x86_64_function in compiler/fission.cpp (AmirModule/AmirFunction are private to that
translation unit, so this could not live in a separate .cpp the way the encoder header does) that
walks a single named function's A-MIR and lowers CONST (string -> UTF-16 via WP-007, placed in a
data section referenced by RIP-relative LEA with a recorded-but-unpatched relocation; integer ->
64-bit immediate MOV), LOAD, CALL_EXTERNAL (walking the UEFI field chain from WP-006, injecting the
implicit "This" argument that uefi-bindings.md flagged as a known gap -- this work package closes
it), and RETURN. Uses a uniform spill-everything register strategy (every named value gets its own
stack slot, always reloaded before use, nothing kept live in a register across instructions) --
exactly the "simple spill-based implementation" Packet WP-008 explicitly permits. Any A-MIR shape
outside this scope (multi-block control flow, an unbound field, a non-integer-literal constant, a
5th+ stack-passed parameter) produces a clear error rather than a silently wrong encoding.

Verified the complete hello-world function's generated bytes two additional, independent ways:
1. Against a hand-written nasm reference implementing the identical instruction sequence (using
   `strict qword` to force the same full-width immediate-MOV encoding the generator uses, since
   nasm's default optimizer would otherwise pick a shorter form) -- every byte matches exactly
   except the deliberately-unpatched relocation placeholder, and the generator's own relocation
   bookkeeping was confirmed by hand to reproduce nasm's computed RIP-relative displacement exactly
   under the same contiguous text-then-rdata layout.
2. Against `objdump -D -b binary -m i386:x86-64 -M intel` (a disassembler from a different
   toolchain than nasm, decoding the generator's raw bytes rather than comparing against
   independently-assembled ones) -- it decodes the generated .text bytes into precisely the
   intended instruction sequence with no gaps or misalignment.

Added a new `ArcoFission reveal FILE at X86_64 [--entry NAME]` stage rendering a deterministic
disassembly-style text dump (hex bytes for .text and .rdata, plus the relocation list) for
diagnostics and golden testing, matching the established AST/A-MIR/BYTECODE/CALLCONV pattern.

ASSUMPTIONS
- The uniform spill-everything strategy is deliberately not optimized; Packet WP-008 explicitly
  permits this ("a simple spill-based implementation is acceptable if deterministic and correct").
- mov_reg_imm64 always uses the full 10-byte REX.W+imm64 form, never the shorter 5-byte reg32,imm32
  form a real assembler would pick for small values -- also a deliberate non-optimization, verified
  against nasm's `strict qword` output rather than its default (auto-shortening) behavior.
- Only register-passed parameters (the first four) are supported; a function needing a 5th+
  stack-passed parameter is rejected with a clear error. The hello-world's two-parameter Main never
  exercises this path.

DEVIATIONS
None from docs/systems/uefi-target.md, calling-conventions.md, or uefi-bindings.md. This work
package resolves (rather than deviates from) the implicit-This-argument gap uefi-bindings.md
explicitly flagged as deferred to WP-008.

REGRESSIONS
None (10/10 tests passing, including all 9 pre-existing tests unchanged).

RISKS
- The relocation is recorded but not patched; WP-009 must correctly compute the final RIP-relative
  displacement once .text and .rdata have real virtual addresses in a PE image, using the same
  formula already verified here (target_address - instruction_end_address). Getting the section
  ordering or alignment wrong at that stage would silently break the LEA despite everything in this
  work package being independently verified correct.
- generate_x86_64_function lives inside compiler/fission.cpp's anonymous namespace (like
  render_calling_convention and other backend logic before it) because AmirModule/AmirFunction/
  AmirInstruction are not exposed via any header. WP-009 will need to either add its own logic in
  the same file/namespace or this constraint will need revisiting; noted here so it isn't
  rediscovered as a surprise.
- Coverage is intentionally narrow (five A-MIR instruction kinds, one block, four register
  parameters). Any future test program shaped differently than the hello-world will hit a clear
  "not supported" error rather than working -- expected and desired per Packet's non-goals, but
  worth remembering before assuming this generator is more general than it is.

NEXT SAFE WORK PACKAGE

WP-001 toolchain survey showing no PE-capable linker on this host), and this work package's
Relocation records are exactly the input WP-009 needs to place .text/.rdata and patch the LEA.
