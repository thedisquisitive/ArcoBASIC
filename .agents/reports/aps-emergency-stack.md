# APS Emergency Stack (IST1)

## Scope delivered

Closed the last gap `aps-tss-emergency-stacks.md` and `aps-gdt-reload.md` both left open: TSS.IST1
now points at a real, dedicated stack instead of zero, and an IDT gate's `IST=1` field is proven to
actually switch the CPU onto it -- not merely that `LTR` accepts a table with a plausible-looking
value in it.

Two new hardware-semantic primitives, needed to test this without engineering a genuine
hardware fault-on-fault condition:

- `CPU.Interrupt(vector)` -- raises a vector directly (`INT imm8`, opcode `CD ib`). `vector` must
  be a compile-time constant, matching this backend's existing `PORT.Offset` precedent for
  operands that must be statically known.
- `CPU.ReloadDataSegments(selector)` -- reloads `DS`/`ES`/`FS`/`GS` in one call (`MOV Sreg, AX`
  four times). Hygiene, not a correctness requirement the way `CPU.ReloadStackSegment` (added in
  `aps-gdt-reload.md`) was: none of these four are touched by interrupt frame push/pop.

New encoder primitives (`arco/x86_64_encoder.hpp`): `mov_ds_rax`/`mov_es_rax`/`mov_fs_rax`/
`mov_gs_rax`, `int_imm8`.

## Two real bugs found proving this, neither in the compiler

Both were genuine gotchas in how this specific proof was constructed, not compiler bugs -- but
both cost real debugging time and are exactly the kind of thing worth recording so they aren't
rediscovered the hard way again.

1. **Software `INT n` never pushes a hardware error code, even for a vector whose fault-raised
   form normally would.** The exception-entry table's per-vector stubs are built once, generically,
   from `x86_64_vector_has_error_code()` -- correct for genuine hardware faults, but vector 8
   (`#DF`) normally has one, so its stub does *not* push a placeholder, assuming the CPU already
   did. Raising vector 8 via `CPU.Interrupt(8)` for testing silently misaligned the entire stack
   frame by 8 bytes underneath the handler. Fixed not by changing the table (which is correct for
   real hardware delivery) but by testing through vector 0 (`#DE`, divide error) instead -- no
   architectural error code, so software `INT` and a genuine hardware fault produce the same stack
   shape. `BuildMinimalIDT` in the proof fixture (not `stdlib/`) sets `IST=1` on vector 0 too,
   test-only, alongside the real vector 8 policy; the exception table's shared handler's IST-switch
   probe dispatches on vector 0 for exactly this reason. This also means vector 8's own IST1
   switch is not directly exercised by *this* proof -- it shares the identical
   `IDTWriteInterruptGate`/`ist` construction path vector 0's successful test just validated, but a
   genuine hardware `#DF` is what would be needed to test vector 8 itself.

2. **A scratch memory address chosen without regard for how much RAM the test VM actually has
   reads back as silent zero, not a fault.** The IST-switch probe records the observed `RSP` to a
   fixed address so ArcoBASIC code can read it back after resuming. The first address tried,
   `0x10000000` (256 MiB), is beyond what `qemu-system-x86_64` allocates by default with no
   explicit `-m` flag (the harness never passes one). The identity map's page-table entry exists
   (any address in the mapped 2 MiB leaf translates), but there is no physical RAM behind it in
   this VM's configuration -- both the write and the subsequent read silently "succeed" against
   nothing, and the missing backing memory is indistinguishable from the probe never having run at
   all. Cost real time: the vector-0-vs-8 error-code bug above was found and fixed *first*, and
   this address issue was still there afterward, masquerading as a second, different failure with
   an identical symptom (a plausible-looking value reading back as zero). Fixed by moving the
   scratch address to `0x2000000` (32 MiB), comfortably under any default QEMU RAM size.

## Validation

- exact encoder unit tests for every new primitive, byte-for-byte against the x86-64 architecture
  encoding;
- structural smoke test (`systems_arco_basic_emergency_stack_smoke.sh`): `CPU.Interrupt` rejects a
  non-constant vector with the expected diagnostic; a minimal fixture's generated bytes contain the
  exact `int $0x8` (`cd 08`) encoding;
- **the real proof, executed under QEMU/OVMF**: `aps-emergency-stack.abas` allocates a genuine
  16 KiB stack via `AllocatePages`, supplies its top to `BuildTSS`'s `doubleFaultStack` parameter,
  activates the full GDT/TSS/IDT chain from `aps-gdt-reload.md`, raises vector 0 via
  `CPU.Interrupt(0)`, and confirms the RSP the exception table's shared handler observed (read back
  from the scratch address afterward) falls within `[dfStackBase, dfStackTop)` -- the dedicated
  stack this fixture built, not the ordinary one. Verified deterministic across repeated runs;
- full existing test suite (44/44) passes.

## Remaining activation gate

Vector 8's own IST1 switch is not directly exercised by a genuine hardware `#DF` -- doing so needs
either engineering a real fault-on-fault condition (delicate, and risks being unreliable across
QEMU versions/hardware) or accepting that the identical, already-proven `ist=1` gate-construction
code is sufficient evidence. The TSS's `RSP0` (ring0 stack, used on privilege-level-changing
interrupts) is still zero -- irrelevant to every proof in this chain so far, since nothing here
ever runs below CPL0, but a real gap the moment ring3 code exists. `DS`/`ES`/`FS`/`GS` reload
(`CPU.ReloadDataSegments`) exists now but nothing in this chain has proven it necessary the way
`CPU.ReloadStackSegment` was -- it is included in `aps-emergency-stack.abas` as hygiene, following
`aps-gdt-reload.md`'s own note that this was left undone.
