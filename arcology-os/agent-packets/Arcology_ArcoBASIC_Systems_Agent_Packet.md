# Arcology OS Autonomous Agent Instruction Packet
## Mission: ArcoBASIC as a Working Systems Language

**Document type:** Autonomous coding-agent execution contract  
**Primary milestone:** Produce a UEFI x86-64 application written in ArcoBASIC that displays `Hello from ArcoBASIC` in a virtual machine without using C or handwritten assembly in project source.

---

# 1. Agent Role

You are acting as an **Implementer**.

You may implement only the architecture and behavior defined by this packet and its referenced specifications.

You must not invent new public language features, redesign existing ArcoBASIC syntax, replace the selected implementation language, or broaden the project scope.

When a material ambiguity blocks correct implementation, stop at the nearest safe checkpoint and report it. Do not silently choose an architecture on behalf of the project owner.

---

# 2. Mission Objective

Extend the existing ArcoBASIC toolchain until it can serve as a minimal freestanding systems language.

The final accepted result must compile a small ArcoBASIC source file into a valid x86-64 UEFI PE/COFF executable that boots under QEMU/OVMF and displays:

```text
Hello from ArcoBASIC
```

The project source for the boot application must contain:

- ArcoBASIC
- project configuration
- tests
- build scripts
- generated files where appropriate

The project source must not require the boot application developer to author:

- C
- C++
- Rust
- assembly
- linker scripts
- raw PE/COFF structures by hand

Compiler implementation code may use the implementation language already used by the current ArcoBASIC compiler.

---

# 3. Architectural Decisions

These decisions are locked.

## 3.1 Systems language

ArcoBASIC is Arcology OS's native systems language.

## 3.2 No handwritten assembly requirement

Developers express hardware and ABI intent through ArcoBASIC language features and standard hardware interfaces.

Machine-specific instructions are generated by compiler backends.

Generated assembly may be emitted for diagnostics, but project developers must not need to author it.

## 3.3 Compilation pipeline

Use this conceptual pipeline:

```text
ArcoBASIC source
    ↓
Lexer and parser
    ↓
AST
    ↓
Semantic analysis
    ↓
A-MIR
    ↓
x86-64 backend
    ↓
PE/COFF image
    ↓
UEFI firmware
```

Do not bypass A-MIR by directly translating the AST into final machine code unless the current compiler architecture already requires a temporary compatibility path. Any temporary bypass must be documented and isolated behind a backend interface.

## 3.4 Initial target

The first systems target is:

```text
Architecture: x86-64
Firmware: UEFI
Binary format: PE32+
Machine type: AMD64
Execution environment: QEMU with OVMF
```

Do not implement legacy BIOS support.

Do not implement ARM64 in this mission.

## 3.5 Initial output mechanism

The first boot application must use the UEFI Simple Text Output Protocol.

Do not implement a framebuffer renderer for the first milestone.

## 3.6 Initial runtime

The first UEFI program uses a minimal freestanding runtime.

No libc or host operating-system APIs may be required at runtime.

## 3.7 Path syntax

Native Arcology paths use `:` as the hierarchy separator.

Host build scripts may use host-native path syntax where required by the host operating system.

Before changing code:

1. Inspect the repository structure.
2. Identify the compiler implementation language and build system.
3. Locate the lexer, parser, AST, type system, semantic analyzer, IR, backend, tests, and documentation.
4. Record the current build and test commands.
5. Run the current test suite unchanged.
6. Create a baseline report.

Do not perform a broad rewrite.

Do not rename public files or directories unless required by an accepted specification.

Do not add a third-party dependency without documenting:

- why it is required
- its license
- whether it is needed at build time or runtime
- why an existing dependency cannot satisfy the need

Prefer no new dependency.

# 7. Minimal ArcoBASIC Language Surface

Use the smallest language surface that can express the milestone.

A preferred source shape is:

```basic
#PROFILE UEFI
#TARGET X86_64
#RUNTIME NONE
#CALLCONV UEFI
#EXPORT "efi_main"

FUNCTION Main(imageHandle AS UEFI.Handle, systemTable AS UEFI.SystemTable) AS U64
    systemTable.ConsoleOut.Write "Hello from ArcoBASIC"
    RETURN 0
END FUNCTION
```

This syntax is illustrative.

If equivalent syntax already exists in ArcoBASIC, preserve existing conventions rather than introducing conflicting syntax.

If new syntax is required, implement only the smallest additions necessary and document them.

Do not add multiple competing spellings for the same concept.

---

# 8. Required Systems Types

Ensure the compiler can represent at least:

```text
U8
U16
U32
U64
I8
I16
I32
I64
BOOL
PTR or an equivalent pointer type
```

For the first milestone, UEFI handles and pointers may use an opaque pointer representation.

Every systems type must have:

- exact size
- deterministic alignment
- documented signedness
- deterministic conversion rules
- tests

Do not introduce implicit narrowing conversions.

---

# 9. UEFI ABI Requirements

The generated application must satisfy the x86-64 UEFI ABI.

The implementation must correctly handle:

- Microsoft x64 calling convention
- UEFI entry point export
- 64-bit pointers
- PE32+ executable format
- correct image subsystem for EFI applications
- stack alignment
- required register preservation
- UTF-16 strings for UEFI text output

The agent must verify these requirements from primary technical specifications or official documentation before implementation.

Do not guess ABI details.

---

# 10. PE/COFF Strategy

Choose one of these strategies in priority order:

1. Use an existing compiler/linker component already present in the repository.
2. Emit an object format supported by an already-approved host linker.
3. Add a small, isolated PE32+ image writer.
4. Add a new external linker only when unavoidable.

Record the selected strategy before implementation.

The public ArcoBASIC developer workflow should remain:

```text
arcofission build hello.abas --target uefi-x86_64
```

or the closest equivalent supported by the current CLI.

The developer should not need to invoke a linker manually.

# 11. Work Package Sequence

Proceed in order.

Do not skip a package because a later package appears more interesting.

## WP-000: Repository Audit

### Objective

Understand the existing codebase and establish a passing baseline.

### Required actions

- Map compiler phases and relevant files.
- Identify the current IR.
- Identify supported output formats.
- Identify existing type definitions.
- Identify test framework and commands.
- Run all tests.
- Record failures that existed before modification.

### Deliverable

`agent-reports:WP-000-repository-audit.md`

### Acceptance

- Repository map exists.
- Baseline build command documented.
- Baseline test command documented.
- Existing failures distinguished from new failures.

### Stop conditions

Stop if the repository is unavailable, cannot build due to undocumented prerequisites, or has no identifiable compiler source.

---

## WP-001: Systems Target RFC

### Objective

Write the minimal implementation specification for the first systems target.

### Required contents

- Target triple or target name
- Freestanding profile behavior
- Required types
- UEFI calling convention
- Entry-point mapping
- PE/COFF strategy
- Runtime assumptions
- Exact hello-world source
- Exact expected output
- Error behavior for unsupported features

### Deliverable

`docs:systems:uefi-target.md`

### Acceptance

The document is precise enough that another agent could implement the target without selecting architecture.

### Stop conditions

Stop if required behavior conflicts with existing accepted ArcoBASIC syntax or compiler architecture.

---

## WP-002: Fixed-Width Types

### Objective

Implement or verify the required fixed-width systems types.

### Required behavior

- Correct sizes and signedness
- Literal range checking
- Clear overflow diagnostics
- Deterministic conversions
- Tests for valid and invalid values

### Acceptance tests

Examples:

```basic
DIM a AS U8 = 255
DIM b AS U16 = 65535
DIM c AS U32 = 4294967295
DIM d AS U64 = 18446744073709551615
```

Must reject:

```basic
DIM a AS U8 = 256
DIM b AS U16 = -1
```

### Non-goals

- Arbitrary precision integers
- Floating-point ABI work
- SIMD types

---

## WP-003: Freestanding Profile

### Objective

Add a compiler profile that assumes no operating system or standard runtime.

### Required behavior

The profile must:

- disable implicit host-runtime dependencies
- reject unavailable runtime features
- allow explicitly supplied external interfaces
- produce deterministic diagnostics

### Acceptance

A trivial function with no host dependencies compiles under the freestanding profile.

A program using an unavailable host-dependent feature fails with a clear message.

---

## WP-004: A-MIR Systems Primitives

### Objective

Extend A-MIR only as required to represent the hello-world UEFI program.

### Required capabilities

- fixed-width integer values
- pointer values
- function parameters
- function returns
- external or ABI-bound function calls
- constants
- structure field access or equivalent offset-safe representation

### Non-goals

- interrupts
- atomics
- MMIO
- inline assembly
- optimizer work beyond correctness

### Acceptance

The hello-world source can be lowered to valid A-MIR and printed in a deterministic textual form.

---

## WP-005: Microsoft x64 Calling Convention

### Objective

Implement the calling convention required by x86-64 UEFI.

### Required behavior

- correct argument registers
- correct return register
- correct stack alignment
- shadow space where required
- preserved registers
- nested calls sufficient for UEFI text output

### Verification

- unit tests for register assignment
- golden tests for generated assembly or machine-code disassembly
- comparison against the ABI specification

### Stop conditions

Stop if the existing backend architecture cannot represent multiple calling conventions without a public redesign.

---

## WP-006: UEFI Bindings

### Objective

Add the smallest safe UEFI surface needed for text output.

### Required entities

- EFI status type
- image handle type
- system table
- simple text output protocol
- output-string function

Do not attempt to bind the entire UEFI specification.

Use typed structures rather than magic offsets wherever the compiler supports them.

### Acceptance

The compiler can type-check the hello-world source and resolve the required UEFI fields.

---

## WP-007: UTF-16 Constant Support

### Objective

Represent the message in the encoding required by UEFI.

### Required behavior

- encode the hello string as UTF-16
- include a terminating null code unit
- preserve constant lifetime for the duration of the call
- reject unsupported source cases clearly

### Acceptance

A test verifies the exact emitted UTF-16 code units.

---

## WP-008: x86-64 Code Generation

### Objective

Generate correct machine code for the limited A-MIR used by the milestone.

### Required behavior

- function prologue and epilogue
- local constant addressing
- pointer dereference
- field offset access
- indirect function call
- return value
- UEFI ABI compliance

### Non-goals

- optimization
- register allocator sophistication beyond correctness
- general-purpose instruction selection

A simple spill-based implementation is acceptable if deterministic and correct.

---

## WP-009: PE32+ EFI Image

### Objective

Produce a valid UEFI-loadable executable.

### Required validation

Use available inspection tools to verify:

- PE32+ format
- AMD64 machine type
- EFI application subsystem
- entry point
- section alignment
- image size
- absence of host runtime imports

### Acceptance

OVMF loads the image without an invalid-image error.

---

## WP-010: QEMU/OVMF Harness

### Objective

Create a deterministic automated run harness.

### Required behavior

- launch QEMU with OVMF
- expose a FAT-formatted EFI system partition or equivalent test image
- start the generated EFI application
- capture serial or display output where practical
- enforce a timeout
- return a nonzero status on failure

### Preferred result

The test command reports:

```text
PASS: Hello from ArcoBASIC
```

### Environment policy

If OVMF is unavailable, document installation requirements and provide a detection error. Do not download firmware silently during tests.

---

## WP-011: End-to-End Milestone

### Objective

Build and run the complete hello-world boot application.

### Required source

The final example must be ArcoBASIC.

### Required output

```text
Hello from ArcoBASIC
```

### Acceptance

- clean checkout builds successfully
- all pre-existing passing tests remain passing
- new systems tests pass
- EFI image is generated
- QEMU/OVMF runs it
- expected output appears
- no handwritten assembly exists in the example
- no C exists in the example
- generated assembly or disassembly is available for inspection

# 14. Agent Assumption Policy

## May decide without stopping

The agent may choose:

- private helper function names
- local file organization consistent with repository style
- internal test fixture names
- straightforward implementation details that do not affect public behavior

Record these choices in the work-package report.

## Must stop and report

The agent must not choose:

- new public ArcoBASIC syntax beyond the minimum required
- a new implementation language
- a new IR architecture
- a new runtime model
- a different target firmware
- legacy BIOS support
- a major third-party dependency
- a breaking change to existing programs

# 15. Stop Conditions

Stop at a safe checkpoint and produce a blocked report if:

- an authoritative specification conflicts with this packet
- the existing compiler architecture makes the requested feature impossible without a major redesign
- baseline tests are broadly failing and cause cannot be isolated
- required ABI details cannot be verified
- a license issue blocks a needed dependency
- generated output cannot be validated
- the task would require modifying unrelated subsystems
- security-sensitive behavior is undefined
- repository data appears corrupt or incomplete

Do not conceal a stop condition by implementing a guess.

# 18. Final Definition of Done

The mission is complete only when all statements are true:

- ArcoBASIC has a documented freestanding UEFI x86-64 target.
- The compiler accepts the approved hello-world source.
- The compiler generates a valid PE32+ EFI application.
- The generated program requires no host runtime.
- The program boots under QEMU/OVMF.
- It displays `Hello from ArcoBASIC`.
- The application source contains no C, C++, Rust, or handwritten assembly.
- ABI and binary format tests pass.
- Compiler regression tests pass or all pre-existing failures are documented.
- Build and run instructions work from a clean checkout.
- The final implementation report accounts for every work package.
